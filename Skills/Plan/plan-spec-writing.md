## 문서 유형

| 문서 유형 | 내용 |
|----------|------|
| 기능 스펙 | 단일 기능의 동작 명세 (입력/출력/규칙/엣지 케이스) |

## 스펙 작성 절차

### 1단계 — 입력 수집

- plan-designer 또는 plan-hub로부터 GDD / 컨셉 문서 수신
- 구현 대상 기능·시스템 범위 확정
- 기술 제약 조건 (플랫폼, 엔진 버전, 성능 예산) 확인

### 2단계 — 스펙 구조 설계

필수 섹션:
```markdown
## [기능명] 스펙 v{버전}

### 개요
- **목적**: 이 기능이 해결하는 문제 / 제공하는 가치
- **범위**: 포함/제외 사항 명시

### 동작 명세
| 상태/조건 | 입력 | 처리 | 출력 |
|----------|------|------|------|

### 수치 파라미터
| 파라미터명 | 기본값 | 범위 | 단위 | 비고 |
|-----------|--------|------|------|------|

### 엣지 케이스
| 케이스 | 예상 동작 |
|--------|----------|

### 의존 관계
- 선행 기능: ...
- 연동 시스템: ...

### 검증 기준 (Acceptance Criteria)
- [ ] 조건 1
- [ ] 조건 2
```

### 3단계 — 수치 근거 명시

- 모든 수치에 단위와 산출 근거 기재
- 밸런스 수치는 초기값 + 조정 범위 명시
- 레퍼런스 게임의 수치와 비교 (가능 시)

### 4단계 — 검토 및 완료

- plan-designer와 교차 검토 (기획 의도와 스펙 일치 확인)
- 구현 에이전트(unity-developer 등)가 바로 착수 가능한 수준인지 확인
- TBD 항목 잔존 시 사유와 결정 일정 명시

---

## 스펙 품질 기준

- 모호한 표현 허용 기준: **없음** (모든 조건은 참/거짓 판별 가능해야 함)
- 구현자가 추가 질문 없이 개발 착수 가능한 완성도
- 검증 기준(Acceptance Criteria)은 반드시 테스트 가능한 형태로 작성
