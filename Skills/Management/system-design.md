# System Design — CTO 설계 주도 프로세스

구현 착수 전 설계 에이전트가 아키텍처를 확정하고, CTO가 검토·승인하는 프로세스.

## 트리거 기준

다음 중 하나라도 해당하면 이 스킬을 선행한다:
- 신규 시스템·Feature·서브시스템 도입
- 기존 시스템 변경 범위가 **2개 이상의 클래스**에 영향
- 새 인터페이스·Bus 메시지·asmdef 추가
- MonoBehaviour → POCO 전환 범위가 2개 이상

## 실행 흐름

### Step 1: 도메인 판별 → 설계 에이전트 선발

| 도메인 | 설계 에이전트 | 참조 스킬 |
|--------|-------------|---------|
| JellyMolly 캐릭터·Feature | `jelly-architect` | `Design\jelly-architecture.md` |
| Unity 일반 시스템 | `unity-architect` | `Dev\unity-architecture-design.md` |
| 복합 | 두 에이전트 병렬 선발 | 양쪽 모두 |

### Step 2: 설계 에이전트에 컨텍스트 전달

- 기능 요청 원문
- 관련 기존 파일 경로
- 설계 산출물 저장 경로: `docs/design/{YYYY-MM-DD}-{feature-name}.md`
- 구현 담당 에이전트명

### Step 3: 설계 산출물 검토

- [ ] 규칙 위반 없음 (SOLID, DI, POCO 원칙)
- [ ] 인터페이스 시그니처 명시됨
- [ ] 의존성 방향 단방향
- [ ] Bus 메시지 필요 여부 판단됨
- [ ] 구현 에이전트에 넘길 수 있는 완성도

### Step 4: 구현 이행 승인

검토 통과 → dev-lead에 설계서 + 구현 에이전트 배치 지시.
검토 불통과 → 설계 에이전트에 재설계 요청 (수정 포인트 명시).

## 에러 핸들링

| 상황 | 처리 |
|------|------|
| 설계 범위 불명확 | 사용자에게 범위 확인 후 진행 |
| 설계 완료 전 구현 요청 | 설계 완료 후 구현 원칙 유지, 사용자에게 안내 |
