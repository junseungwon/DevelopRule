## 기획 작성 원칙

### Lead Planner (총괄 기획)

1. 기능은 플레이어 경험(가치) 관점에서 먼저 정의. 구현 방법은 나중
2. 모든 기능은 측정 가능한 완료 조건을 가진다
3. MVP → 확장 순으로 단계화
4. 세부 동작·엣지케이스는 detail-planner에 위임

#### 총괄 기획서 형식

```markdown
# {기능명} 기능 스펙

## 개요
{기능의 목적과 플레이어 경험 관점 설명 (3줄 이내)}

## 성공 기준
- {측정 가능한 완료 조건 1}
- {측정 가능한 완료 조건 2}

## 우선순위
| Feature | 우선순위 | 비고 |
|---------|---------|------|
| {Feature 1} | P0 | MVP 필수 |
| {Feature 2} | P1 | MVP 이후 |

## 리스크
- {기술적 제약·리스크 1}
```

### Detail Planner (세부 기획)

1. Feature의 입력 → 처리 → 출력 흐름 정의
2. 상태 전이, 조건 분기, 예외·엣지케이스 열거
3. 수치·시간·쿨타임은 반드시 값 또는 조정 범위 명시
4. 구현 방식(코드 구조)은 architect 책임. 간섭 금지

#### 세부 기획서 형식

```markdown
# {Feature명} 세부 기획서

## 동작 흐름
{입력} → {처리 1} → {처리 2} → {출력}

## 상태 전이표
| 현재 상태 | 조건 | 다음 상태 |
|---------|------|---------|

## 파라미터
| 파라미터명 | 타입 | 기본값 | 조정 범위 |
|-----------|------|--------|---------|

## 엣지케이스
- 비정상 입력: {설명}
- 동시성: {설명}
- 리소스 실패: {설명}
- 상태 경계: {설명}

## UI/UX 시나리오
{플레이어가 보고 느끼는 것 중심으로 기술}
```

## 에러 핸들링

| 상황 | 처리 |
|------|------|
| 요구사항 모호 | 사용자에게 최소 질문으로 확인 |
| 범위 과다 | MVP 범위 제안 후 확정 |
| 상위 스펙 불명확 | lead-planner에게 반려 |
| 기술적 실현 불가 우려 | architect에 타당성 확인 요청 |
